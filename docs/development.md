## Dev environment

Everything is installed with [pixi](https://pixi.sh) (`pixi.toml`, platforms `osx-arm64` and `linux-64`): Python 3.12,
nf-core tools, nf-test, pre-commit, pytest, ruff, jinja2, pandas, pyyaml. The pipeline's own tools run in per-process
containers or conda environments, not in pixi. You also need Nextflow >= 26.04.0 and Docker (the dev machine is macOS +
Docker Desktop; production is Linux + Docker; keep `docker`, `singularity` and `conda`/`mamba` profiles working).

```bash
pixi install
pixi run pytest tests/python
pixi run ruff check bin tests && pixi run ruff format --check bin tests
pixi run pre-commit run --all-files
```

The Freyja and most bioconda images are `linux/amd64` only: on Apple Silicon the `docker` profile adds
`--platform=linux/amd64` automatically (slow, emulated). Conda on macOS is unreliable; use `-profile docker` there.

## The test layers

Cheapest first. The CI jobs are described in [ci.md](ci.md).

| Layer             | Command                                                                                                                       | Needs          | What it covers                                                                                                                                                                                                                                                                                                                                                               |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pytest            | `pixi run pytest tests/python`                                                                                                | nothing        | all `bin/` scripts, report data/renderer, samplesheets, the bump/lock scripts, the typed-boolean-params consistency, "every Freyja pin agrees". About 440 tests (the count grows; 441 at the time of writing), about 10 s.                                                                                                                                                   |
| nf-test, stub     | `pixi run nf-test test --tag stub --profile test_stub --ci --verbose`                                                         | Nextflow       | wiring and output layout of every module and mode with `-stub` (no tool runs).                                                                                                                                                                                                                                                                                               |
| nf-test, docker   | `pixi run nf-test test --tag docker --profile=+docker --ci --verbose`                                                         | Docker         | real tool runs of each module and of the pipeline on the synthetic data (`--barcodes container`, offline). Slow (tens of minutes).                                                                                                                                                                                                                                           |
| canary            | `pixi run nf-test test --tag upstream_canary --profile=+docker --verbose`                                                     | Docker         | passes while plain `freyja plot` is still broken upstream; **fails when upstream is fixed** (then remove the workaround in `FREYJA_AGGREGATE_PLOT`, PLAN D6).                                                                                                                                                                                                                |
| end to end        | `tests/e2e.sh <scratch dir> [nextflow args]`                                                                                  | Docker         | `full` (with `--compare_barcodes container --freyja_boot --annotate_variants`) -> `demix --previous_results` (byte-identical demix files, aggregate and statuses; previous dir untouched) -> `demix` on a legacy Snakemake layout -> `aggregate` (two ways) -> `report --results_dir` (HTML equals the original modulo timestamps), with `check_outputs.py` after each step. |
| demix equivalence | `tests/demix_equivalence.sh <scratch dir> [nextflow args]`                                                                    | Docker         | the narrower PLAN section 8 test: `full`, then `demix` with the same barcodes must give identical `.demix`, aggregate and status files, also from a legacy layout.                                                                                                                                                                                                           |
| output checks     | `python tests/check_outputs.py <outdir> --mode full\|demix\|aggregate\|report [--extras compare,boot,annotate] [--truth ...]` | Python >= 3.12 | tolerance-based checks of an output directory against `tests/data/truth.json` (lineage abundances within +-0.05, absent lineages below 0.05, QC flags, consensus status, negative-control handling, the extras' tables, report self-containment).                                                                                                                            |

Details worth knowing:

- Pass **pipeline params through the CLI or `-params-file`**, not through custom `-c` files (nf-schema validates params).
- Tests are tagged `stub` (every test run with `-stub`) and `docker` (every real test); CI selects by tag and fails if a
  tag selects nothing. Tag new tests accordingly.
- `e2e.sh` also runs the probe-capture dataset (`--protocol capture`, with and without duplicate marking) and `--skip_primer_trimming`; `check_outputs.py --protocol capture` checks it. `e2e.sh` and `demix_equivalence.sh` run each Nextflow command from its own `<scratch>/launch_<step>` directory, with
  its own `.nextflow` and work directory, so nothing pollutes the repo (the `block-pipeline-outdir` pre-commit hook
  refuses output in the repo). Do the same for ad-hoc runs: **never launch Nextflow from the repo root.**
- Snapshots: `pixi run nf-test test <file> --update-snapshot` regenerates `.snap` files. A Freyja bump rewrites the
  Freyja version stamp in the snapshots by itself; any other snapshot change after a bump needs a human decision.
- The synthetic data tests are deterministic: they pass `--barcodes tests/data/barcodes_test.csv` or
  `--barcodes container`, so they need no network. Only `--barcodes latest` needs one.
- Samplesheet paths in `tests/data/samplesheet.csv` are relative to the repo root; the test profiles must be launched
  from the repo root, or pass a samplesheet with absolute paths (what `e2e.sh` does with `sed`).

## Regenerating the test data

`tests/data/` (about 3 MB) is generated, deterministically, by `tests/make_test_data.py` (standard library only);
full description in [test_data.md](test_data.md).

```bash
pixi run python tests/make_test_data.py --out tests/data --seed 42
pixi run pytest tests/python/test_make_test_data.py      # checks reproducibility and that tests/data is current
pixi run python tests/make_test_data.py --protocol capture   # tests/data_capture (probe capture; see test_data.md)
pixi run pytest tests/python/test_make_capture_data.py
```

The barcode subset `tests/data/barcodes_test.csv` is extracted once from a real Freyja barcode CSV (the `--extract-barcodes`
option; the procedure with the Freyja container is in test_data.md). Regenerating the reads needs only the committed
subset. After a regeneration review the diff of `truth.json`, then update the nf-test snapshots and run `e2e.sh`.

## How to add things

### A local module

1. `modules/local/<name>/main.nf` with the process name in `UPPERCASE_WITH_UNDERSCORES`, a `label` from
   `process_single|low|medium|high`, an exact-pinned `container` (never `latest`; the docker/singularity ternary used by
   the other local modules) and `conda "${moduleDir}/environment.yml"`, a `stub:` block, and software versions emitted
   through the `topic: versions` tuple (`tuple val("${task.process}"), val('tool'), eval('tool --version ...'), emit: versions_tool, topic: versions`).
2. `modules/local/<name>/environment.yml` with the pinned conda package (same version as the container tag).
3. `modules/local/<name>/tests/main.nf.test` with a `stub` test (tag `stub`) and a real test (tag `docker`).
4. Script logic goes in `bin/<script>.py` (stdlib + pandas only) with a pytest file in `tests/python/`.
5. Wire it in `workflows/wasteline.nf`, and add publishing and options in `conf/modules.config` (nothing is published
   unless listed there). Decide the error strategy: a step that must not fail the run uses `errorStrategy = 'ignore'`
   and the workflow records a status row for the sample.
6. Update `docs/output.md` if it writes files, and run `python bin/lock_containers.py --update` if it adds a container.

A failed or skipped sample must produce a row with a status and a reason; it must not abort the run or yield an empty
file that looks like a result.

### A parameter

1. Default in `nextflow.config` (`params {}`), snake_case.
2. Entry in `nextflow_schema.json` in the right group (`pixi run nf-core pipelines schema build`, then
   `schema lint`), with description, help text and bounds.
3. If it is a boolean or number: add it to the typed `params { ... }` block in `main.nf` (Nextflow >= 26.04 hands CLI
   parameters over as strings; the block converts them). `tests/python/test_boolean_params.py` fails when the block and
   `nextflow.config` disagree.
4. Use it in `conf/modules.config` (`ext.args`/`ext.*`) or the workflow.
5. Add it to `docs/parameters.md` (the page is checked to list exactly the schema's parameters) and, if a user-facing
   behaviour, `docs/usage.md`.

### A primer scheme

1. Add `assets/primer_schemes/<name>.bed` (6-column BED; contig name equal to the reference contig, `NC_045512.2`; primer
   names with `_LEFT/_RIGHT`, `_F/_R` or `F/R` suffixes so `bin/amplicon_coverage.py` can derive the amplicons; see
   `docs/qc_scripts.md` for the naming rules and special cases).
2. Add the name to the `primer_scheme` enum in `nextflow_schema.json` and to `docs/parameters.md`.
3. Add its expected amplicon count to `test_bundled_scheme_amplicon_counts` in `tests/python/test_amplicon_coverage.py`.
4. If it needs an ivar offset (as `swift` does with 5), set it in `conf/modules.config` (`IVAR_TRIM`) and the
   `ivarOffset()` helper in `subworkflows/local/utils_nfcore_wasteline_pipeline/main.nf`.
5. For a one-off scheme, users can already pass `--primer_bed`; no code change is needed.

## Bumping Freyja

Freyja is the one tool that is bumped automatically (PLAN D1, section 9). It is pinned (container tag, Galaxy depot
singularity URL, `environment.yml`) in the `freyja_*` modules, and `bin/bump_freyja.py` knows every pin.

**Automatic:** `.github/workflows/freyja-update.yml` runs daily. If a newer release exists on quay.io biocontainers,
bioconda and the Galaxy depot, it creates branch `bot/freyja-<version>`, applies the bump (pins, version stamps in
tests/snapshots, a line under `CHANGELOG.md` > Unreleased > Dependencies), refreshes the digest lock and opens a PR.
Same-major bumps auto-merge once `ci-required` and `pre-commit` pass; a new major stays open (`needs-review`). The
repository settings this needs (secret `BOT_TOKEN`, auto-merge, branch protection) are in [ci.md](ci.md).

**Manual:**

```bash
python bin/bump_freyja.py --require-consistent          # offline: do all pins agree?
python bin/bump_freyja.py --check                        # pinned vs latest (network)
python bin/bump_freyja.py --apply --dry-run              # what would change
python bin/bump_freyja.py --apply                        # rewrite pins + CHANGELOG to the latest release
python bin/bump_freyja.py --apply --tag 2.0.4--pyhdfd78af_0   # explicit tag; also the way to roll back
python bin/lock_containers.py --update                   # refresh conf/containers.lock.config
pixi run pytest tests/python/test_bump_freyja.py
pixi run nf-test test --tag docker --profile=+docker --ci   # the real tests on the new Freyja
```

After a bump check the `upstream-canary` job: if it fails, a Freyja release fixed plain `freyja plot` and the workaround
in `FREYJA_AGGREGATE_PLOT` (and the canary) should be removed (PLAN D6). Barcode **data** is not part of a bump: it is
resolved per run with `--barcodes`.

The script appends its line under the **`### \`Dependencies\``** heading of the first `## ... unreleased/dev ...`section of`CHANGELOG.md`; keep that heading and a section whose title contains `Unreleased`or`dev`, or it creates them.

## Rebuilding the report renderer image

`RENDER_REPORT` needs Python and Jinja2, and no biocontainer ships Jinja2 (it is conda-forge only), so its image is built
from `modules/local/render_report/environment.yml` with the [Seqera Wave CLI](https://github.com/seqeralabs/wave-cli) in
freeze mode, which stores it in Seqera's free community registry (`community.wave.seqera.io`; no account needed, images
are public and kept for years). Only repeat this when `environment.yml` changes:

```bash
# download a release binary from https://github.com/seqeralabs/wave-cli/releases and check it against checksums_sha256.txt
wave --conda-channels conda-forge --conda-package python=3.12.12 --conda-package jinja2=3.1.6 \
     --platform linux/amd64 --freeze --await                       # prints community.wave.seqera.io/library/python_jinja2:<hash>
wave --conda-channels conda-forge --conda-package python=3.12.12 --conda-package jinja2=3.1.6 \
     --platform linux/amd64 --singularity --freeze --await         # prints oras://community.wave.seqera.io/library/python_jinja2:<hash>
```

Put the two printed names in `modules/local/render_report/main.nf`, run `python bin/lock_containers.py --update`, and
re-run `nf-test test modules/local/render_report --profile docker`. The current images were built with Wave CLI 1.8.2 from
Python 3.12.12 and Jinja2 3.1.6 (Docker `...:b2615084ab562e7a`, Singularity `oras://...:c7f3fc5ddefd422e`).

## Container digest lock

`conf/containers.lock.config` maps every process to an immutable `registry/repo@sha256:` digest and is used with
`-profile docker,locked` (reproducible runs; recorded images then are digests). It is generated, never hand-edited:

```bash
python bin/lock_containers.py --check                    # offline: is the lock stale?
python bin/lock_containers.py --update                   # (re)write; unchanged pins are not re-resolved
python bin/lock_containers.py --check --verify-digests   # re-resolve every digest against the registries (network)
```

CI runs `--check` on every PR (non-blocking) and `--verify-digests` weekly. Change a container pin => run `--update`.
The lock covers digest pinning only; it has not been tested with Singularity (docs/ci.md). `run_info.json` records the
images from the run itself (not by reading the lock file).

## nf-core lint caveats

```bash
pixi run nf-core pipelines lint
```

- Lint wants a git repository with at least one commit (**`nf-core pipelines lint` needs a commit**, so lint a committed copy as below rather than the working tree). It also **modifies files** (for example it re-syncs the RO-Crate
  description from the README and generates the one-line `conf/containers_*.config` files). Lint a committed **copy**
  rather than the working tree:

  ```bash
  rsync -a --exclude .git --exclude .pixi --exclude '.nextflow*' --exclude .nf-test ./ /tmp/wasteline-lint/
  (cd /tmp/wasteline-lint && git init -q -b main && git add -A && git commit -qm lint)
  pixi run nf-core pipelines lint --dir /tmp/wasteline-lint
  ```

- Verified on this tree (nf-core tools 4.1.0): 0 failed, about 21 warnings, of which the README/CHANGELOG `TODO` strings
  and outdated-module/subworkflow notices are the known ones. The intentional exceptions are in `.nf-core.yml` (MultiQC
  is not used, template strings in the report template, ...). `nf-core pipelines lint --release` fails on a `dev`
  version by design; CI's `nf-core-lint` therefore never uses `--release`.
- `nextflow lint` runs in pre-commit on `*.nf` and `nextflow.config`. The pixi environment lives in `.pixi/` inside the repo:
  `nf-core pipelines lint` ignores it, but `nextflow lint .` descends into it and reports errors from the Nextflow files of the
  installed packages. Point it at specific paths instead, for example
  `nextflow lint main.nf workflows subworkflows/local modules/local nextflow.config` (never the repo root: `nextflow lint .` reported "9 files had 11 errors" here, with the specific paths above 0 errors).
- Never edit the template-synced files that lint compares (`files_unchanged` in `.nf-core.yml`) without adding them to
  its exception list.

## Branch flow

`dev` is the working branch; `main` is the release branch. Open PRs against `dev`, and only `dev` (or `patch`) may PR into
`main` (the template's `branch.yml` enforces this). Do not commit or push unless you mean to. Freyja bump PRs target the
default branch (see ci.md). Releases are made from `main` and bump `manifest.version`
and the CHANGELOG date.

## Conventions

From `CLAUDE.md`; the short version:

- Process names: nf-core modules `UPPERCASE`, local modules `UPPERCASE_WITH_UNDERSCORES`. Params `snake_case`.
- Labels `process_single|low|medium|high`.
- Pass pipeline params through CLI flags or `-params-file`, not custom `-c` files.
- Every local module has `main.nf`, `environment.yml`, a `stub:` block, version reporting and an nf-test.
- Every container is pinned to an exact tag; never `latest`. Freyja is the one tool bumped automatically.
- Sample IDs are never rewritten (the old pipeline turned `_` into `-`; we do not).
- A failed/skipped sample gets a status row with a reason; it never aborts the run or yields an empty result file.
- No hard-coded `NC_045512` / SARS-CoV-2 strings outside `conf/pathogens/sars2.config` and `assets/`.
- Freyja >= 2.0 barcodes are `usher_barcodes.feather` (1.x used `.csv`); `freyja variants` runs `samtools mpileup | ivar
variants` itself and ivar may append `.tsv`, so verify output names; `freyja aggregate` takes a directory with a trailing
  slash and labels samples by file name; `--freyja_varthresh` defaults to Freyja's 0.0, not the old 0.25.
- Nextflow >= 26.04 only: named `-entry` workflows are rejected by the strict parser (hence `--mode`), and CLI booleans
  arrive as strings (hence the typed params block in `main.nf`).

## The pathogen-agnostic structure

Pathogen-specific defaults live in one file, `conf/pathogens/sars2.config`, loaded by `nextflow.config`:

```groovy
params {
    pathogen = 'SARS-CoV-2'   // Freyja --pathogen name
    fasta    = "${projectDir}/assets/references/NC_045512.fasta"
    gff      = "${projectDir}/assets/references/NC_045512.gff3"
}
```

The reference and annotation can already be replaced on the command line (`--fasta`, `--gff`, `--primer_bed`), and no
SARS-CoV-2 strings or coordinates are hard-coded in the pipeline code (`bin/`, `modules/local`, `workflows`; only in
tests and `assets/`), except the report subtitle ("Wastewater SARS-CoV-2 lineage deconvolution" in
`assets/templates/report.html.j2`). **But the groundwork is not enough to run another pathogen today.** What adding
one would take:

1. `conf/pathogens/<name>.config` with the reference, annotation and Freyja `pathogen`, and a way to select it
   (currently `nextflow.config` includes `sars2.config` unconditionally; a `--pathogen`-driven include is needed).
2. `--pathogen` is validated against a one-value enum (`SARS-CoV-2`) in `nextflow_schema.json`; widening it is part of adding a
   pathogen. `params.pathogen` is already passed to `freyja update`, `freyja demix`, `freyja boot` and `freyja plot` (`ext.args`
   in `conf/modules.config`) and to `FREYJA_DATASET_INFO`; `freyja variants` and `freyja aggregate` are called without it.
   <!-- verified by reading conf/modules.config and modules/local/freyja_*/main.nf -->
3. Dataset handling: `FREYJA_UPDATE` copies the SARS-CoV-2 file names from the container (`usher_barcodes.feather`, ...) and
   `freyja_dataset_info.py` looks for `usher_barcodes.*`; other pathogens ship different data files (`pathogen_config.yml`).
4. Primer schemes and amplicon logic for the new target (`assets/primer_schemes/`, naming rules in `amplicon_coverage.py`).
5. QC assumptions: thresholds tuned for SARS-CoV-2 amplicon schemes, the consensus length and mask logic (single contig),
   and the report text. Segmented or multi-contig genomes are not supported (the depths/coverage tracks use the first
   contig).
6. Test data, truth, tests and docs for the new pathogen.
