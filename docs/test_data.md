# Synthetic test dataset

`tests/data/` holds a small (about 3 MB), deterministic, synthetic wastewater dataset used by the nf-test suite and
the pytest suite (PLAN section 8). It is generated by `tests/make_test_data.py` (pure Python standard library).

## Regenerate

```bash
pixi run python tests/make_test_data.py --out tests/data --seed 42
pixi run pytest tests/python/test_make_test_data.py
```

Output is byte-identical for the same seed, reference, primer BED and `barcodes_test.csv` (gzip written with
`mtime=0` and no filename; only `random.Random.random()` and `gauss()` are used). `pytest` generates twice into
temporary directories and compares file hashes, and checks that the committed `tests/data` matches a fresh
generation (FASTQ compared after decompression so a different zlib build cannot cause a spurious failure).

## How the reads are made

1. **Lineage genomes**: each lineage's barcode SNVs from `barcodes_test.csv` are applied to
   `assets/references/NC_045512.fasta`. Mutations whose reference base does not match, that conflict at one position,
   or whose notation is not an SNV are skipped and counted (printed at generation time and stored in `truth.json`
   under `lineage_mutation_application`). In the shipped barcode data (version below) every barcode mutation is an
   SNV and none are skipped. Freyja's barcodes contain no deletions or insertions, so the simulated genomes have none.
2. **Amplicons** come from the primer BED (default `assets/primer_schemes/midnight.bed`; 29 amplicons): left-most
   forward primer start to right-most reverse primer end, grouped by primer name without the `_F`/`_R` (or
   `_LEFT`/`_RIGHT`) suffix. Tested with `midnight` and `articv4.1`.
3. **Per-amplicon depth** is log-normally jittered (sd 0.35); dropped amplicons get zero reads.
4. **Fragments** (length ~ N(300, 40), clipped to 200-450) are anchored at the amplicon 5' end (20%), 3' end (20%)
   or placed uniformly inside the amplicon (60%), so that a large share of reads begin with the primer (for `ivar trim`)
   while the middle of ~1.2 kb amplicons is still covered by 2x150 reads. The primer-binding ends of every amplicon
   carry the reference (primer) sequence, not the lineage sequence, as in real amplicon data.
5. **Reads**: 2x150, random strand, error rate 0.002 per base (60% of errors get Q12, the rest Q30), Q37 for most
   bases with a mildly lower 3' tail (Q32/Q27).

## Barcode subset (`barcodes_test.csv`)

Source: Freyja container `quay.io/biocontainers/freyja:2.0.5--pyhdfd78af_0`, bundled barcode version
`09_17_2026-00-46` (`last_barcode_update.txt`). Lineages (all present in the container's `lineages.yml`):
`B` (reference-like, no mutations), `B.1`, `B.1.1.7`, `B.1.351`, `P.1`, `AY.4`, `BA.1`, `BA.2`, `BA.5`, `BQ.1.1`,
`XBB.1.5`, `EG.5.1`, `JN.1`, `KP.3`. Only columns (mutations) that are non-zero for at least one chosen lineage are
kept; the format is Freyja's `--barcodes` CSV (unnamed index column = lineage, one column per `<ref><pos><alt>`
mutation, values `0.0`/`1.0`). The extractor refuses lineages missing from `lineages.yml` and lineages with identical
barcodes.

Extraction (one-off; the 100 MB source file is not committed):

```bash
D=/usr/local/lib/python3.12/site-packages/freyja/data
mkdir -p /tmp/freyja_data
docker run --rm --platform linux/amd64 -v /tmp/freyja_data:/out quay.io/biocontainers/freyja:2.0.5--pyhdfd78af_0 \
    sh -c "cp $D/usher_barcodes.csv $D/lineages.yml $D/last_barcode_update.txt /out/"
pixi run python tests/make_test_data.py --extract-barcodes /tmp/freyja_data/usher_barcodes.csv \
    --lineages-yml /tmp/freyja_data/lineages.yml --barcodes tests/data/barcodes_test.csv
```

(The container ships `usher_barcodes.feather` as well; the CSV is used because `--barcodes` accepts `.csv`.)
Regenerating the reads needs only the committed `barcodes_test.csv`.

## Validation with real tools (Freyja 2.0.5 container)

Reads were mapped with `bwa mem` (`quay.io/biocontainers/bwa:0.7.17--he4a0461_11`, which has no samtools; the Freyja
container has no bwa), sorted with the Freyja container's samtools, then `freyja variants` and
`freyja demix --barcodes tests/data/barcodes_test.csv` (default `--eps`, no trimming). Recovered abundances
(Freyja's `lineages`/`abundances` output):

| Sample | Truth | Recovered | Genome >= 10x | Mean depth |
|---|---|---|---|---|
| `MIX_A` | BA.2 0.70, AY.4 0.30 | BA.2 0.709, AY.4 0.291 | 99.5% | 57x |
| `MIX_B` | BA.1 0.50, XBB.1.5 0.30, KP.3 0.20 | BA.1 0.512, XBB.1.5 0.268, KP.3 0.191, BA.2 0.029 (spurious) | 99.5% | 66x |
| `PURE_C` | JN.1 1.00 | JN.1 1.000 | 99.5% | 76x |
| `Site_1_week_2` | BA.5 0.60, XBB.1.5 0.40 | BA.5 0.607, XBB.1.5 0.359, BA.2 0.034 (spurious) | 93.5% | 62x |
| `LOWCOV_D` | BA.2 1.00 | BA.2 1.000 (but Freyja reports `coverage` 0.0) | 0.0% | 0.6x |
| `NEG_E` | none | Freyja `demix` crashes (see below) | 0.0% | 0.0x |

All true lineages are recovered within about 0.03 of truth (tolerance in `truth.json`: 0.05; the small spurious BA.2
fractions in `MIX_B` and `Site_1_week_2` are the only extra calls, <= 0.034). Note that Freyja collapses lineages in its
`summarized` output, so JN.1 is summarised as `BA.2.86*`; compare on the `lineages`/`abundances` rows.

Observations relevant to the pipeline:

- At very low depth Freyja still demixes happily and reports a confident result (`LOWCOV_D`: BA.2 = 1.0 from about 0.6x
  depth, `coverage` 0.0). The pipeline's coverage gate is therefore what prevents a meaningless result being reported.
- For `NEG_E` (6 mapped reads, `freyja variants` writes a header-only TSV) `freyja demix` exits with a pandas
  `TypeError: operation 'radd' not supported for dtype 'str' with dtype 'object'`. The coverage gate must prevent
  demix from running on such samples (or the failure must be recorded as `failed` with a reason).
- `freyja variants` wrote `<prefix>.tsv` when given `--variants <prefix>` (as warned in CLAUDE.md).
